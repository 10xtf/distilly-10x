# Agent Note: productize the host-LLM workflow in Design V3

Status: proposed

## Problem

Design V2 established the right product boundary — local facts, multiple subjects, evidenced claims, version lineage, a zero-extra-key host path, a TypeScript engine, and a small public facade — but its specified plugin path could not execute the product acceptance test from a clean installation.

The five MCP tools had no way to create the first subject, force an immediate distillation boundary, or retrieve the material content needed to construct a draft. Pending jobs exposed only ids, hashes, and counts while hostBriefing existed only as an internal engine method. The draft let an untrusted host submit claims and unrelated Markdown as two competing truths. Evidence validation required a non-empty list but did not require the referenced material to exist, belong to the subject and generation, or contain the quoted text. A 32-bit material digest simultaneously carried identity, deduplication, evidence, and lineage. The plugin manifest assumed a distilly executable was already on PATH, and the local panel was optional even though users had no other product surface for inspecting evidence or resolving a risky candidate.

V2 also made two semantic promises that do not survive the decision to use a host LLM for research and distillation. New evidence can contradict old evidence, so profile quality does not monotonically rise with material count. Two external models can produce different evidence-bounded proposals from the same input; the deterministic obligation belongs to the engine's hashing, validation, patch application, rendering, and version transaction, not to pretending the external sampler is byte-stable.

These gaps cross the product workflow, wire contract, value types, file format, package cut, installation, review surface, and release order. Continuing to patch V2 would leave a historical design whose locked decisions mean two incompatible things. The repository's design-corpus rule exists for exactly this situation: add the next self-contained parent and preserve the old one as deprecated history.

## Proposal

[docs/design/system-v3.md](../../../../docs/design/system-v3.md) becomes the only in-force target contract. [system-v2.md](../../../../docs/design/system-v2.md) and its generated chapters remain readable, are marked deprecated, and are not rewritten to match V3.

V3 makes the product chat-first and local-reviewable:

- The host LLM plans research, uses capabilities the host actually has, reads a typed briefing, and proposes a claim patch.
- The local engine owns subject ids, full SHA-256 content digests, material ids, deduplication, generation leases, evidence resolution, claim ids, quality summaries, deterministic Markdown, current versus suspended state, version transactions, and recovery.
- The model-facing surface keeps exactly five names: get, ingest, pending, commit, and correct. Ingest carries a discriminated create target and enqueue=now; pending carries list, brief, renew, and release. This closes the workflow without adding create, flush, research, or briefing tools.
- Briefing is the only legal host-distillation input. It atomically acquires a generation lease and returns the baseline claims, complete incremental materials, provenance, short evidence handles, prompt/schema/source-grouping versions, and explicit size limits. A full BriefContract digest is pinned in the lease and echoed by commit, so a runtime upgrade cannot silently reinterpret the host's evidence before quality is calculated. It never silently truncates.
- The host submits add, revise, supersede, and contest claim operations. It does not submit claim ids, actor, confidence, version ids, or Markdown. Claims are the semantic truth; Markdown and prompt text are deterministic projections.
- Commit hard-rejects invalid generation, lease, subject ownership, material membership, quote, locator, and patch shape. A structurally valid candidate that changes identity, loses coverage, introduces conflicts, or disagrees with a correction becomes suspended. Clean candidates become current without a compulsory click.
- The local Panel ships in the first usable release. It provides Library, Subject, Review, and Settings/Doctor pages over the same EngineClient. It renders engine-owned facts, never reads the fact directory, and preserves the loopback, per-run token, Origin, Host, and single-write-path security boundary.
- Setup installs a versioned runtime and an absolute launcher before it writes host manifests. A fresh plugin no longer relies on a pre-existing global executable or an unpinned npx latest invocation.
- Plugin Source, Local Library, and the future remote Profile Catalog are separate concepts. The first release has no account, remote sync, publish API, or Discover placeholder. A remote catalog enters only after the local bundle, provenance, consent, moderation, and import-as-suspended contracts are proven.

The local fact model changes accordingly. MaterialId, full ContentDigest, and a full ProvenanceDigest are distinct, and material identity is no longer reused as a claim of source independence. MaterialId incorporates source identity, grouping/security/export-relevant provenance, and content, so the same URL/body with different access, derivation, or privacy semantics cannot become a first-writer-wins record. Source carrier, artifact locator, narrow representation-of provenance, and text derivation are persisted separately. The `material-text-v1` and namespaced source-identity preimages close line-ending, Unicode, default-array, URI-priority, and NUL ambiguities before those values enter a digest. A versioned engine function collapses the same raw input, artifact, canonical URI, exact republication, and derived caption/OCR/transcript representations into source groups; unknown provenance is retained as evidence but cannot inflate diversity. Every structured fact carries a kind-specific schemaVersion and full FactChecksum over canonical JSON. Subject state stores the sorted current material manifest and authoritative pending-job marker, while each immutable version stores the same material-entry shape for historical membership; neither current nor historical grouping is guessed from directory contents.

Request idempotency is a root fact rather than a subject-directory convenience. One root request lock serializes a RequestId across method and space, a completed OperationRecord carries an engine-owned global-or-subject scope, and one discriminated OperationFact path also admits a content-free privacy tombstone. The first TransactionRecord union member is a root IngestTransactionRecord with explicit space, subject, create-versus-existing checksum invariants, new material entries, operation result, and events. Existing subjects commit by atomic state swap; create publishes one fully staged subject directory from a request-and-subject-named staging path. Recovery checks the target first, including the equal-previous-and-target duplicate case, before it may abort to the proven previous or absent state and remove only journal-named material/staging. An aborted request can re-enter prepared only for the same input and actor and must reuse its candidate subject id; completed operations and committed transactions replay immutably. Prepared records are never abandoned by elapsed time, and the first format does not invent automatic retention for successful operations or terminal journals.

Privacy purge cannot make many files change simultaneously on an ordinary filesystem. It therefore records a prepared purge transaction, recoverably replaces each affected subject-scoped operation with a tombstone and deletes each related transaction journal, and publishes a final purge commit point only after the list is complete. Journal-only requests receive a tombstone too. A same-input replay after purge returns not-found while a changed input or actor remains an idempotency conflict, so deletion neither retains the successful payload nor reopens a used RequestId.

Creation has a wider uniqueness boundary than later writes. A root catalog lock serializes inline space resolution by kind plus an exact versioned label; a space-scoped identity lock then serializes the fact-backed duplicate check before the candidate subject lock. The reserved People record gives every installation the same one exceptional non-random SpaceId and is bootstrapped by create-exclusive-or-exact-readback. Label-v1 deliberately preserves case and internal bytes, while exact locators outrank exact canonical display/alias candidates; one non-conflicting name candidate fails conservatively with remediation, multiple candidates remain ambiguous, and a proven same-kind locator disagreement excludes a candidate. Description never proves identity. Identity-locator-v1 intentionally starts with an empty case-insensitive provider table: provider ids normalize, but every handle keeps its case until a later version has explicit provider evidence and migration fixtures. Every path follows request → optional catalog → space identity → subject → fact commit → SQLite projection, so two different candidate ids cannot both create the same identity and no SQLite transaction waits while holding the inverse order. RequestId is frozen as `req_` plus 32 lowercase hexadecimal characters: enough caller-generated entropy for retries, directly safe as the root operation, lock, and transaction filename, and narrow enough that slash, separator, and dot-segment strings fail before path construction.

Recovery is also part of the writer protocol rather than a startup-only hope. Each ingest reconciles visible prepared root journals before taking its own request lock, then rechecks under its space/subject locks. If another request prepared the same subject or a create in the same space during that window, the new writer releases its locks and retries from the top; it never waits for another request lock while holding its own. This closes the crash window without reversing the global lock order.

Automatic queueing uses one auditable `auto-v1` rule: three uncommitted materials or a 30-minute-old uncommitted material, evaluated only when an ingest attempt holds the subject lock. The baseline is the verified current-version manifest, or empty when no current version exists; it is not duplicated into state or SQLite. An existing same-generation marker is reused, while a new generation replaces an older pending marker regardless of the threshold. Queue SQLite remains a disposable projection of state.pending. A fixed-byte dirty marker brackets each post-commit database apply, and rebuild writes a durable sibling database from every verified pending marker before replacement; a missing/corrupt database cannot masquerade as an empty queue.

Lease truth therefore lives with the pending job in SubjectStateRecord schema version 2, not in that disposable database. A PendingLeaseMarker carries an engine-generated per-client owner, acquisition/expiry times, and the complete BriefContract. Expiry is a read-time clock predicate rather than a timer mutation: an expired marker reads as pending, can be replaced by the next brief, and emits no synthetic expiry event. Brief, renew, and release use a method-correlated root DistillLeaseTransactionRecord whose atomic state swap is the commit point. The journal retains both complete pending markers, state checksums, the exact OperationRecord, and one job.changed EventRecord, so target-first recovery can only finish the target, abort the exact previous state, or fail as corrupt. A brief operation deliberately retains the complete, size-bounded briefing: exact idempotent replay is more important than regenerating content under possibly changed prompt, material, or capacity facts, and subject purge removes that payload through the normal tombstone path.

The queue projection uses user version 2 for its lease-aware public read fields. Opening the earlier user-version-1 projection treats it as unavailable and rebuilds from verified state version 2 instead of pretending an ALTER migration can restore facts that never lived in the old table. QueueRepository only applies, reads, lists, and rebuilds verified state seeds; it never acquires or mutates leases. Rebuild takes a lazy seed supplier and invokes it only while holding the projection lock. A writer that commits state during that snapshot consequently either appears in the snapshot or applies its row after rebuild, preventing a clean-but-stale database.

The first grouping and briefing contracts are byte-addressed rather than implementation labels. `source-groups-v1` unions exact raw, private-conversation, artifact/representation locator, fallback source-URI, and content proof keys; component ids hash the sorted unique key set, while diversity eligibility uses only public artifact or fallback source-URI proof and fails closed on access conflict. The prompt version hashes the raw prompt asset together with the exact ordered evidence rules, including the model-facing prohibitions against obeying material-supplied commands or disclosing environment, configuration, secrets, and other subjects. BriefContractDigest hashes exactly the source-grouping, prompt, and draft-schema fields. Host capacity is trusted session context after binding-envelope overhead, not a model parameter. A complete compact canonical briefing uses a conservative byte-equals-token fixed point and must fit both host budgets, the 4 MiB internal cap, and 999 material references before any journal or lease write.

Immutable versions store claims as one checksummed VersionClaimsSnapshot rather than an append-looking jsonl file. The verified reader cross-checks that snapshot with the version record, historical material manifest, each material body, and every evidence quote and Unicode-scalar locator. VersionId hashes the canonical claims with `createdIn` removed, then assigns the resulting id to claims created in that version; this preserves creation lineage without defining an impossible self-referential digest.

The commit boundary is now closed as its own recoverable fact transaction rather than an implementation placeholder. A DistillCommitTransactionRecord retains the exact accepted claim-only patch and digest, lease owner, proven previous state/pending marker, complete target state, immutable version/material/claims/Profile/prompt payloads, method-correlated operation result, canonical review reasons, and exactly two events. The only staging path is `versions/.staging/<request>.<version>`; state replacement is the commit point. Recovery can finish the fully matching target, abort the fully matching previous state while deleting only journal-matching and unreferenced staging/published output, or fail as corrupt. A proven published abort target is first atomically renamed to a fixed journal-owned `.deleting` path before recursive removal, so another crash cannot strand a partially deleted directory at a fact-visible VersionId path. The single public wire/runtime schema owns patch byte, shape, local date-range, and locator-range rejection before durable lookup; state-dependent target, cycle, and evidence checks retain their narrower later precedence instead of requiring a second permissive parser. Because success deletes the disposable queue row, retained commit journals provide the durable job-to-subject locator needed to preserve active-review precedence on a later ordinary commit; they do not become a second pending queue. Hard reject writes nothing and preserves the lease, while either successful disposition consumes pending: current replaces current with no suspended target, and suspended preserves current while naming the new candidate. LeaseOwnerId participates in commit idempotency so a different client cannot replay another session's lease-bound mutation.

Claim application and rendering are also byte contracts. Commit rebuilds its narrow EvidenceContext from verified state, base version, manifests, and material bodies using the lease-pinned algorithms; it does not depend on retaining or searching a previous brief OperationRecord. A canonical resolved draft deduplicates and orders evidence and observations, validates time ranges, targets each base claim at most once, and derives ClaimId from `claim-v1` plus subject and resolved draft. Empty patches are valid; add/revise create active claims, revise records the replacement edge, supersede does not invent one, and contest preserves the historical id/text/createdIn while merging evidence. Quality and review reasons use exact set/count/delta rules and canonical ordering, including suspicious/manual gates on a first version. Step 7 deliberately has no relationOperations; relations enter additively in their later slice instead of occupying a disabled runtime field.

`profile-renderer-v1` is a literal, injection-safe projection contract: seven core roots stay in fixed order, domains and claims use UTF-8 ordering, active and contested claims are explicit, superseded claims are omitted, and dynamic claim text is carried only inside canonical JSON records. Every section, combined profile, and prompt ends in one LF. Each immutable version stores profile.md, seven core files, domain files, and prompt.md; current is only an atomically rebuilt projection. Profile snapshots the version-time display name, VersionRecord stores the same subjectDisplayName and includes it with canonical review reasons in the VersionId preimage, and renderPrompt reads only Profile. A later SubjectRecord rename therefore cannot rewrite or make unverifiable a historical prompt.

Local lock recovery chooses safety over forcibly reclaiming a process that may resume. An expired heartbeat is necessary but not sufficient: while the recorded local owner PID still exists, the lock remains busy. Once the owner is confirmed dead, stale reclaimers rename the lock through a deterministic, non-empty fence derived from the old inode and owner token. The fence prevents an arbitrarily delayed reclaimer from removing a successor; normal release uses a transient retired path and leaves no fence. Portable Node filesystem APIs do not provide the compare-and-unlink primitive needed to both delete every crash fence and remain safe against a suspended old reclaimer, so these small fences are retained only on the dead-owner recovery path.

The rest of the Protocol surface is closed with the same rule rather than leaving each entry point to invent validation. Random subject, space, job, lease, lease-owner, event, and capture references carry a named prefix plus 128 bits; content-derived raw, version, claim, and relation ids carry a named prefix plus a full SHA-256. Times use one UTC millisecond representation, host names and facet paths have portable ASCII grammars, and briefing evidence handles are the bounded m001..m999 namespace. Public object schemas reject unknown keys, use safe integers, and share conservative byte and collection limits for model-controlled input. JSON error details are recursively JSON-safe, while subject-creation collisions use a code-correlated typed resolution instead of an undocumented details payload. Empty EngineMethodMap results are explicit null, so in-process, disk operation records, MCP, HTTP, and later RPC do not disagree about how to serialize `void`.

The five MCP descriptors are also Protocol data, not presenter copy. One ordered registry binds each exact name to its title, local-only description, runtime input/output schemas, draft-2020-12 JSON Schemas, and all four MCP hints. Runtime and JSON schemas derive from one source and are snapshotted together. The text deliberately describes only local lookup, storage, leases, validation, commit, and correction: host research remains the outer workflow and is not falsely attributed to a tool. Get and pending actions have closed action-to-result mappings, and unknown future EngineEvent kinds fail decoding, skip handlers, and cause a full read-model refresh rather than leaking an untyped event into consumers.

V3 remains intentionally conservative about abstraction. External variation uses TypeScript interfaces: EngineClient, QueueRepository, SourceAdapter, MaterialParser, HostBinding, HostInjector, DraftProducer, and LibraryProjection. Stateless algorithms are pure functions. Single production implementations are concrete services. The public API exports no abstract classes and no generic StorageProvider.

The package graph separates the fact engine from local product composition. Engine depends only on protocol and ultimately exposes a core runtime; `@distilly/runtime` composes parser registries, host bindings, doctor aggregation, and the full EngineMethodMap. File ingest remains engine-owned because raw storage, subject locking, material insertion, generation, and queueing are one fact transaction; runtime supplies only a narrow parser port. A vertical slice uses package-internal composition until every CoreEngineClient method has a real handler: it does not export a partial `createEngine`, install placeholders, or route ingest(create) through a standalone empty-subject handler. Once complete, `createEngine({root})` and `createLocalRuntime({root})` have production defaults, while optional ports and registries remain test or extension overrides. MCP and Panel receive actor-bound EngineClient instances and never import stores. Request ids travel in a required mutation context, actor and briefing capacity come from the trusted client/session boundary, and every non-user correction — including MCP host and ordinary SDK callers — receives relayed provenance and is suspended rather than labeling itself as a direct user action.

Source acquisition and private screen authorization are refined by [the private UI capture Agent Note](2026-08-20-private-ui-capture.md). That follow-on decision preserves the five-tool, host-LLM architecture while separating public research, derived text provenance, engine-owned source grouping, and a strictly consented one-to-one private-message lane.

Review cardinality is explicit: one subject has at most one active suspended target. New material may continue to ingest, but another brief/commit or rollback waits for promote, reject, or a correction that explicitly targets and replaces the candidate. A replacement keeps the current version as its parent/CAS baseline, records the old candidate as its content-derivation edge, rejects that old candidate, and creates the new current or suspended target atomically. Immutable version records retain only their created disposition; current/suspended/historical/rejected status is derived from state and events, so review does not mutate historical version files.

The initial Node support window is closed in this decision at `^22.19 || ^24`. This deliberately admits the two LTS lines exercised by the first CI matrix and rejects Node 23/25, which are EOL, plus Node 26 while it remains Current; the Node project recommends production applications use Active or Maintenance LTS releases ([Node.js releases](https://nodejs.org/en/about/previous-releases)). `22.19` is the frozen oldest fixture, not a claim that every earlier Node 22 build is known broken. Setup preflight, the CI matrix, package metadata, and both host fresh-install fixtures must move together if that support policy changes; it is no longer an implementation-time open question.

Local bundle evidence is also closed. A bundle omits complete private materials but includes the minimum shareable excerpt fact for every exported EvidenceRef. Import re-derives local MaterialIds, revalidates each quote, rewrites references, and suspends the candidate. A profile with dangling evidence is not importable.

The document generator registers V1, V2, and V3 as separate corpora and validates the entire registry before writing any chapter. Parent paths, version-directory pairs, chapter directories, and output files must be unique, and exactly one corpus must be in force. This prevents a mistaken V3 directory from silently overwriting deprecated V2 projections.

## Alternatives considered

- **Continue editing V2** — rejected because the executable workflow requires changing locked wire names and meanings, material identity, draft authority, quality semantics, panel priority, and plugin bootstrap at once. Calling both shapes V2 would hide a major break and erase why the old alternative lost.
- **Add separate create, flush, and briefing MCP tools** — rejected because the user-confirmed product surface keeps five memorable tools. Discriminated actions in ingest and pending close the same workflow without exposing internal service granularity.
- **Let the host submit a complete Profile and arbitrary Markdown** — rejected because evidence can be valid while prose invents unsupported facts. Claim patches plus deterministic rendering leave one semantic truth.
- **Persist only a draft hash and regenerate commit outputs during recovery** — rejected because pinned algorithms, display names, renderer bytes, event ids, and accepted-patch interpretation can change after prepare. The complete journal makes target finish and previous abort independently provable without rerunning semantic work.
- **Reconstruct commit evidence handles from the stored brief operation** — rejected because privacy purge can tombstone that replay payload and operation lookup is not the lease authority. Verified state, base/version manifests, and material facts contain the narrow durable facts needed to reproduce m001 mappings under the pinned contract.
- **Leave relationOperations in DistillPatch behind a disabled feature flag** — rejected because every runtime schema and caller would prematurely own an unusable field, and a future implementation could accidentally accept then drop relation changes. The relation slice adds its discriminant, facts, transaction, and tests together.
- **Render free-form Markdown or rebuild historical prompts from the current SubjectRecord** — rejected because model text can inject structure and later renames would mutate historical output. Canonical JSON records plus a version-time displayName make every stored profile and prompt byte-verifiable.
- **Exclude LeaseOwnerId from commit idempotency** — rejected because the same public params could then replay a mutation bound to another client session's lease. The trusted checksum includes the engine-owned owner even though the owner never appears in public params.
- **Use an LLM judge for confidence and approval** — rejected for the first release. It adds another key/cost path and still cannot guarantee consistency. The engine exposes explainable counts and mechanical review reasons; the user resolves semantic risk in the Panel.
- **Count every MaterialId, URL, OCR result, caption, or transcript as an independent source** — rejected because different material identity does not prove independent origin. Exact and provenance-linked representations remain separately inspectable but collapse into engine-owned, diversity-eligible source groups; unknown origin under-counts rather than inflates corroboration.
- **Require every candidate to be manually approved** — rejected because it turns chat-first maintenance into a click queue. Mechanical-risk candidates are suspended; clean candidates advance automatically and remain reversible.
- **Keep the Panel optional until after the SDK** — rejected because evidence and suspended versions need a trustworthy user surface. A tool-only release can create data the user cannot inspect or recover comfortably.
- **Host a remote MCP backend to qualify for a public plugin directory** — rejected because it would turn a platform distribution limitation into a cloud identity store. Local/repo distribution is the first lane; platform support can later be added in HostInstaller without changing facts.
- **Treat a Git repository as the whole installer** — rejected because manifests do not install the engine, resolve PATH, negotiate protocol versions, or make upgrades atomic.
- **Use symlinks to share the canonical skill** — rejected because archives and target platforms do not preserve them consistently. Release assembly copies from one source and verifies content digests.
- **Build the remote Profile Catalog in the first version** — rejected because accounts, consent, copyright, moderation, impersonation, takedown, signatures, and update policy would delay validation of the core research-to-recall loop.
- **Introduce abstract base classes and a generic storage provider now** — rejected because there is one fact format and no demonstrated inherited state machine. Interfaces and composition preserve the extension seams without freezing implementation inheritance.
- **Use `^22.19 || >=24` as a rolling Node range** — rejected because it silently labels every future major supported before CI and host fixtures qualify it. Supporting only Node 24 was also rejected for the first release because the required CI/host matrix includes the Node 22 LTS line; adding Node 26 later is an explicit support decision, not a semver side effect.
- **Infer current material membership by scanning directories and lock create only by its candidate SubjectId** — rejected because a crash can leave a renamed material ahead of state, and two concurrent creates choose different candidate ids. A state manifest plus prepared journal makes the state checksum decisive; a space identity lock protects the shared uniqueness predicate.
- **Keep operations and journals below each subject** — rejected because RequestId is a process-wide wire identity, not a per-subject namespace. Root records plus one request lock detect cross-method/space reuse and let recovery discover every prepared writer without scanning a guessed subject first.
- **Delete successful operation payloads outright during privacy purge** — rejected because the same RequestId could then be reused as a new mutation. A content-free tombstone preserves only enough checksum/scope metadata to return not-found for the same request and conflict for a changed one.
- **Time out prepared journals or automatically garbage-collect terminal idempotency facts** — rejected because wall-clock age does not prove a writer cannot resume or that a result is no longer replayable. Recovery and explicit purge are the only first-version cleanup authorities.
- **Case-fold/fuzzy-match names or silently create alongside one exact name candidate** — rejected because both choices can merge or split identities without evidence. Exact versioned labels, locator disagreement, and typed remediation keep the ambiguity visible.
- **Run an enqueue timer or store a second collection baseline in SQLite/state** — rejected because it introduces another authority and background lifecycle. Ingest-attempt evaluation against the verified current-version manifest makes state.pending the only durable queue truth.
- **Use SQLite conditional acquire as lease authority** — rejected because deleting or rebuilding `.index` would change ownership truth and could make a previously completed brief impossible to replay. State.pending.lease and a recoverable state transaction keep facts independent of the projection.
- **Store a content-free brief receipt and regenerate the briefing on retry** — rejected because material facts, prompt assets, grouping implementations, and host capacity can change after the commit point. The original bounded briefing in OperationRecord is the only exact method result; privacy purge removes it when the subject is removed.
- **Store version claims as jsonl or one envelope per claim** — rejected because file existence cannot prove a complete snapshot and a truncated tail could look like a smaller valid profile. One checksummed VersionClaimsSnapshot gives an explicit complete-set boundary.
- **Precompute all queue rebuild seeds before taking the projection lock** — rejected because a writer can commit state and queue between that snapshot and database replacement, after which rebuild clears dirty on a stale database. Lazy locked iteration preserves the post-commit apply order.
- **Migrate the Step 5 queue table in place to user version 2** — rejected because the old disposable schema has no authoritative lease columns to migrate. Rebuilding from verified state is simpler and preserves the fact/projection boundary.
- **Reclaim a lock from a still-live process after TTL alone, or delete its stale-recovery fence immediately** — rejected because a suspended local process can resume after a successor starts and a delayed reclaimer can otherwise rename that successor. Without a portable filesystem compare-and-unlink primitive, dead-owner confirmation plus a retained deterministic crash fence is the smallest fail-closed choice; normal releases do not accumulate fences.
- **Allow arbitrary RequestId strings and hash them only when choosing a filename** — rejected because it creates a second identity mapping solely to repair an unsafe wire contract. One strict 128-bit hex wire form is portable, validates before path construction, and remains stable across all transports.
- **Keep other branded ids opaque and let each package choose regexes and limits** — rejected because ids cross file paths, schemas, snapshots, and transports. Divergent acceptance would make a value valid in one client and corrupt or unreachable in another; one portable wire grammar and one conservative limit table are cheaper than compatibility repair.
- **Use `void` in EngineMethodMap and special-case it per transport** — rejected because JSON cannot represent undefined as a required result value, while operation facts already need a stable payload. Explicit null is the smallest language-neutral result and facades may still discard it for ergonomic `Promise<void>` methods.
- **Hand-write MCP runtime schemas, JSON Schemas, titles, and annotations in the server package** — rejected because tools/list could drift from the types accepted by handlers. A single Protocol registry keeps model-facing copy local-only, schema dialect and hints reviewable, and snapshots meaningful.

## Acceptance criteria

- Design V3 is self-contained: a first-time implementer can find the product journeys, trust boundaries, five wire schemas, value ownership, storage commit point, recovery, SDK methods, package tree, interfaces, pure functions, concrete services, Panel contract, installer, security constraints, migration, and release gates without consulting V2.
- The design generator creates all V3 topic chapters from the parent, marks V1 and V2 deprecated, marks only V3 in force, and fails before writing when corpus paths or outputs collide.
- Every current authority link in root instructions, documentation maps, review guidance, development/testing guidance, and active Agent Notes points to V3 by topic. Historical statements that V2 introduced TypeScript remain historical rather than being blindly rewritten.
- A fixed host fixture can execute a clean-store, no-extra-key path through exactly five MCP tools: resolve, ingest with create and enqueue=now, pending brief, claim-only commit, get, and correct.
- Briefing contains the complete incremental generation and fails explicitly when too large. A lease acquired by one client cannot be acquired by another, expires recoverably, and becomes stale when new material arrives.
- Lease owner and full BriefContract survive queue deletion in state.pending.lease; brief/renew/release recover target-first from their method-correlated journal, and same-request replay returns the exact stored briefing or conflicts when owner/capacity changes.
- Lease renewal preserves the same BriefContract digest; commit after a runtime upgrade either uses the pinned source-grouping/draft contract or fails explicitly when that implementation is unavailable. The same patch under different contracts cannot collide on VersionId.
- Commit rejects an unknown, cross-subject, out-of-generation, or quote-mismatched evidence reference and never writes a candidate for rejected input.
- Commit rebuilds its EvidenceContext and m001 mapping from verified state/base/material facts under the lease-pinned algorithm, not from a brief operation lookup; 65,536 canonical patch bytes pass and 65,537 fail with zero writes, while invalid target/date/locator/evidence and unavailable pinned algorithms return their exact error codes without consuming pending or lease.
- A valid clean candidate becomes current; an identity, coverage, voice-example, contested-claim, correction, or source-diversity risk becomes suspended while the old current remains readable.
- The accepted claim-only patch has byte-stable empty/add/revise/supersede/contest semantics, canonical evidence and observedIn ordering, one operation per base claim, exact `claim-v1` ids, exact strength/quality counts, canonical gate reasons, and no relationOperations before the later relation slice.
- Claims, quality summary, Markdown, prompt, version, event, and current pointer are engine-derived and reproducible from the same accepted patch and fact snapshot.
- A DistillCommitTransactionRecord round-trips the complete previous/target and output package; every crash point resolves only to a verified target finish, a verified previous abort with exact unreferenced cleanup, or storage_corrupt. Success consumes pending/lease, emits exactly the version event followed by job.changed, and exact replay cannot transfer across LeaseOwnerId.
- `profile-renderer-v1` has fixed core/domain/status ordering, canonical-JSON dynamic records, injection fixtures, and one trailing LF for every artifact. Profile.displayName equals immutable VersionRecord.subjectDisplayName and historical profile/prompt bytes survive a later SubjectRecord rename.
- Each version has one sorted, checksummed claims snapshot whose evidence is verified against its historical manifest and normalized material bodies; VersionId derivation has no `createdIn` cycle.
- Different URLs with identical content remain different MaterialIds but share a source group; captions/OCR/transcripts derived from one artifact share a group; unknown provenance does not increase eligible diversity; grouping is order-independent and versioned with QualitySummary. Critical provenance changes produce distinct MaterialIds, while each version's material manifest makes its historical grouping reproducible.
- Every EngineMethodMap method has a canonical params/result type and runtime schema; mutation methods require a requestId context, and the protocol contract fixture typechecks every method and five ToolOutput envelopes.
- Every branded value has one accepted wire grammar; IsoDateTime, HostName, FacetPath, and BriefMaterialRef have boundary fixtures; all public object schemas reject unknown keys and share the same WIRE_LIMITS, safe-integer, and JSON-value rules.
- The 35 EngineMethodMap keys have an exact mutation/query partition and JSON-round-trippable results; empty success is always null, and OperationRecord keeps each method correlated with only that method's result.
- tools/list returns exactly the ordered five-registry descriptors, including reviewed title/description copy, draft-2020-12 input/output schemas, and readOnly/destructive/idempotent/openWorld hints; get and pending actions cannot return another action's success shape.
- already_exists returns one typed subject, ambiguous_subject returns at least two typed candidates, and other errors cannot carry subject resolution or non-JSON details. An unknown EngineEvent is not delivered to a handler and causes a schema_unsupported full reread.
- Space, subject, state, material, version, event, operation, and transaction facts have runtime schemas for their FactEnvelope; current and historical manifests share the same sorted entry type, and checksum/schema/path mismatches fail before any write.
- A crash at any ingest step recovers target-first to exactly the previous/absent or target state; aborted same-input retries reuse the candidate id, a committed request returns the stored IngestResult and event ids, queue rebuild reconstructs every pending JobId, and an orphan material without journal proof is never silently adopted or deleted.
- Queue user version 1 never receives an in-place pseudo-migration; a projection-lock-held lazy rebuild from verified state version 2 cannot finish clean-but-stale and preserves each unexpired lease.
- Two processes creating the same identity in one space cannot both succeed; People/bootstrap, inline-space catalog and exact duplicate rules are deterministic; lock ordering is fixed; and malformed or reused-across-method/space RequestIds are rejected before an unsafe write.
- MCP, Panel, and CLI can share one local runtime while retaining host/user actor identity per client; Panel materials and doctor views use typed methods rather than reading the fact directory.
- Once all core handlers exist, `createEngine({root})`, `createLocalRuntime({root})`, and `openInProcess(...)` are constructible without callers importing internal concrete repositories or registries; earlier slices keep their composition internal, and file ingest stores raw input inside engine and crosses only a parser port.
- At most one suspended target exists per subject; stale-parent promotion and rollback during active review fail with review_conflict; candidate replacement records its separate derivation edge; version.json remains byte-immutable through promote/reject.
- MCP correct has no unreachable current branch, while host/sdk/executor/system correction is mechanically suspended with relayed provenance and user correction retains direct-user provenance.
- Exported bundle claims have locally verifiable excerpt evidence after import; no dangling external MaterialId survives.
- The first usable release cannot be declared before fresh-install setup, both host bindings, the local Panel, security refusal tests, and next-chat Recall pass from built artifacts.
- The first release performs no Distilly account login, Profile Catalog network call, hidden sync, background executor start, or telemetry upload.

## Risks

- V3 is deliberately detailed and can be mistaken for shipped behavior. Every entry document must retain the target-versus-live distinction, and architecture.md must change only with implementation.
- A claim-only deterministic renderer may initially sound less polished than free prose. The mitigation is to improve claim quality and renderer templates while keeping every factual sentence traceable, not to restore a second unconstrained prose truth.
- The 30-minute first lease may be wrong for some hosts. The returned expiry and renew action make the behavior visible; changing the internal default within the same semantic contract does not require a wire break.
- Incremental briefing retains baseline claims instead of every historical material body. A revision that needs an old quote can retain the existing EvidenceRef; a full semantic reconsideration is an explicit, size-bounded redistill. Tests must catch accidental claim loss.
- Cross-process locking and a file commit journal add implementation work before the Panel. This is unavoidable once MCP, Panel, and CLI can write concurrently; pretending there is one writer would make the first productized release corruptible.
- A live but wedged local writer is not forcibly evicted, PID reuse can conservatively delay recovery, and a process crash during lock ownership leaves a small deterministic fence. These are fail-closed availability and disk-cleanliness costs of preventing an expired or delayed writer from deleting a newer owner's facts without relying on a platform-specific advisory-lock extension.
- The current material manifest makes each state rewrite O(n) in that subject's material count, and the space identity lock serializes creates within one space. The first release accepts both costs because reads need an authoritative membership set and creates are short, rare critical sections; measured pressure can justify a new fact format, not a directory scan or weaker uniqueness rule.
- Root idempotency facts and content-free tombstones intentionally accumulate in the first format, while request/catalog locks and prepared-journal checks add contention to writes. This is the explicit cost of deterministic replay, recoverable privacy purge, and uniqueness; retention or finer locking needs a separately verified schema/protocol change.
- Auto-v1 has no timer, so a two-item set older than 30 minutes queues only on the next ingest attempt, including a duplicate-only attempt. The product must describe this as attempt-driven batching rather than implying a background executor exists.
- Conservative wire limits can reject an unusually large single material, correction, patch, or briefing even when a particular host could carry it. The product must return the exact failed boundary and remediation; raising a shared limit requires updating both runtime and JSON schema snapshots, while large research sets should be split across ingest calls rather than silently accepted by only one entry point.
- Importing a public bundle as suspended adds friction. Trusting a remote profile directly as local current would be worse because provenance policy, moderation, and publisher identity are outside the local engine's authority.
- Platform plugin rules can change. V3 isolates current distribution facts in the plugin chapter and keeps the engine independent, but release maintainers must re-check official host documentation before publishing.
- Superseding all current authority links is a wide documentation diff. Mechanical link and generated-chapter gates do not prove the prose is still historically accurate, so the final review must distinguish live authority from historical V2 references.
