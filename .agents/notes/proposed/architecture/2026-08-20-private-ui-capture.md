# Agent Note: bound private UI capture to one foreground consented scope

Status: proposed

## Problem

Distilly can research public figures and creators through public web pages, posts, captions, transcripts, OCR, and user-provided files. A private contact is different. The useful source may be a one-to-one message thread visible only in a signed-in desktop application, and a capable host such as Codex may be able to inspect that application through Computer Use. Treating this as another SourceAdapter or as ordinary vision would erase the important boundaries: whose account and thread may be opened, which range may be read, whether unrelated messages are visible, how the host processes screen frames, and whether screenshots become permanent local facts.

Operating-system Screen Recording or Accessibility permission proves only that the host can operate the computer. A host-level “Always allow” choice likewise does not prove that the user consented to process a particular conversation for profile distillation. Chat text cannot carry a trustworthy `consent=true` flag because the model and on-screen content are both untrusted at the authorization boundary. Group chats, attachments, links, audio, and background scrolling also add participants and side effects that the first implementation cannot reliably isolate.

The target therefore needs a host-owned authorization seam and an engine-owned provenance stamp before private UI material can enter the same ingest, briefing, evidence, and commit path as other text. This is a new privacy and trust decision, separate from the general Design V3 workflow recorded in [the Design V3 Agent Note](2026-08-20-design-v3.md).

## Proposal

Private UI capture is an optional HostBinding capability with a narrower contract than the host platform may technically allow. It is foreground-only, one-shot, user-attended, read-only, and bounded to an exact application and account, an exact one-to-one thread, a canonical existing-or-create subject target, and a visible-message or time range. The purpose is fixed to profile distillation and the first release is text-only. A create target is not persisted during authorization; the subject and first transcript batch remain one atomic ingest.

Before the first screen frame is captured, a trusted native host UI displays the complete scope, discloses that the host will process screen content, states what Distilly will retain, asks the user to attest that they have authority to process the selected content, and obtains an explicit confirmation. The product does not claim that this attestation verifies the other participant's consent or establishes a legal basis. Completion, cancellation, idle timeout, screen lock, account/thread/window change, scope escape, or client close invalidates the grant. Expanding the range requires another grant.

The host binding owns a `PrivateUiCaptureController`. Its trusted UI returns either a typed refusal or a non-serializable, one-shot grant handle whose live status can be checked before every frame and revoked on any boundary change. `LocalRuntime` registers a host-native, user-gesture action and composes the controller, a narrow liveness adapter, and an engine-owned capture session. The coordinator atomically binds the handle once, opens the engine session, drives Computer Use, submits one logical transcript batch through `IngestService` with engine-owned `enqueue="now"`, completes the audit, and returns a typed ingested/refused/aborted/failed result to the current host task. Duplicate-only capture still returns an existing or newly upserted pending job when the full set has undistilled changes. This action is not listed in MCP `tools/list`; the five model-facing schemas gain no grant or audit field, generic `EngineRuntime.connect` carries no capture privilege, and the public SDK cannot construct or replay the trusted context.

The engine alone creates the unpredictable `CaptureAuditRef`, stores the normalized subject target in session memory, computes keyed scope and conversation identifiers, writes content-free start/stop events, and stamps accepted material. The capture session enforces a closed cross-field shape: transcript, conversation, private access, personal communication, `computer_use_transcript`, and private sensitivity. It rejects public/shareable labels, web/article carriers, caller-provided URI/artifact/thread/account fields, a second request, or a target that differs after canonicalization. Every written start has exactly one closed stop: successful ingest completes normally, a controller/guard failure preserves its trusted revoke reason, an engine rejection writes `ingest_rejected`, an active-guard coordinator exception uses parameterless abort to write `coordinator_aborted`, and crash recovery writes `process_terminated`; no caller supplies a reason or count. A successful create records the engine-generated SubjectId atomically; a duplicate or ambiguous create closes the grant and requires fresh authorization for the selected existing target.

The host isolates the target window or region and closes notifications before capture. It fails closed on a wrong account or thread, another-chat sidebar exposure, notification, OTP, payment data, secret, or inability to maintain isolation. Operations are read-only: no send, reply, reaction, delete, forward, download, link opening, or settings change. The UI discloses that scrolling may affect read state. Every on-screen instruction remains untrusted data and cannot widen the scope or alter the tool sequence.

The first implementation rejects group chats and attachments, images, audio, files, and links. It retains only the normalized private transcript, the MaterialRecord provenance, and content-free audit events. Screenshots, recordings, clipboard contents, credentials, thread names, and account labels do not enter RawStore, logs, telemetry, or diagnostic bundles. The audit keeps only an installation-keyed scope digest, host, versioned data-policy and retention disclosures, start and stop times, a closed stop reason, engine-derived accepted counts, and trusted guard boundary counts. The caller cannot report its own audit totals or free-form outcome. Distilly's local-first claim applies to its own storage; it does not claim that a host never processes or retains screen frames under the host's data controls. If the binding cannot disclose that policy, cannot gate each frame in a scoped window/region, or cannot return the action result to the current task, the capability is unsupported.

Source diversity uses a separate installation-keyed `ConversationSourceKey`, never the grant id or a bare hash of low-entropy labels. A controller-provided stable opaque application/account/thread locator keeps the same conversation grouped across grants and label changes; if the binding cannot provide one, the engine conservatively groups all private captures for that SubjectId. Private conversation groups are never diversity-eligible. The HMAC key is installation-scoped across MCP, Panel, CLI, and restarts, is never exported or logged, and cannot be silently regenerated if lost because doing so would inflate one conversation into several apparent sources.

The grant cannot be used by a lifecycle hook, scheduled task, subagent, background or locked-mode run, or DistillExecutor. An executor may distill materials already present in the fact layer but may not reopen the private application. Revoking a grant stops future capture; withdrawing or privacy-purging the stored materials is a separate fact-layer action.

This boundary follows the platform guidance that Computer Use on macOS requires Screen Recording and Accessibility permissions, may process screen, screenshot, window, keyboard, and clipboard data, should be scoped to the needed application/window, and exposes approval choices including “Always allow” ([OpenAI Computer Use documentation](https://learn.chatgpt.com/docs/computer-use)). Distilly deliberately adopts the stricter per-conversation rule instead of treating the platform's maximum capability as the product default.

## Alternatives considered

- **Treat operating-system permission or “Always allow” as conversation consent** — rejected because capability permission does not identify the subject, thread, range, purpose, or retention policy and can outlive the user's immediate intent.
- **Let the model submit `consent=true`, a CaptureAuditRef, public/shareable access, or an `independent` source flag in MaterialInput** — rejected because chat and screen content are untrusted and would be able to forge the very provenance the audit is meant to prove.
- **Make private messaging a SourceAdapter** — rejected because a provider adapter suggests reusable background collection and vendor credentials, while this lane is an attended host UI operation with per-run consent and screen-leak risk.
- **Expose capture as a sixth model-facing MCP tool** — rejected because a model tool cannot itself prove the native user gesture, first-frame gate, non-replayable grant, or live window/thread boundary. The host-native action returns to the same canonical workflow without weakening the five-tool contract.
- **Allow rolling, background, locked-screen, lifecycle-hook, subagent, or executor capture** — rejected even if a host platform supports those modes. The user cannot continuously verify the active account, thread, notifications, and scope.
- **Capture the full screen or retain screenshots/raw recordings by default** — rejected because unrelated chats, notifications, credentials, and third-party data would become durable facts without improving the normalized text evidence path.
- **Support group chats and attachments in the first implementation** — rejected because participant separation, author attribution, downloading, malicious files, and raw-media retention each require an additional consent and provenance design.
- **Treat the user's authority attestation as verified participant consent** — rejected because Distilly cannot establish the other participant's consent or make a legal determination from a checkbox.
- **Forbid all private-contact material** — rejected because user-provided or precisely consented one-to-one text is a high-value source and can use the same evidence-bounded profile pipeline once capture is isolated from collection automation.

## Acceptance criteria

- A synthetic host fixture cannot capture its first frame until trusted UI confirms the exact app/account, one-to-one thread, canonical existing-or-create subject target, range, text-only purpose, host-processing disclosure, Distilly retention, and user authority attestation.
- Screen Recording, Accessibility, or a prior “Always allow” choice never bypasses the per-scope confirmation.
- The grant expires on completion, cancellation, timeout, lock, account/thread/window change, boundary escape, or client close; a larger range requires another grant. Atomic bind prevents replay, and revocation after authorization but before ingest is rechecked by the engine.
- Wrong-account/window, another-chat sidebar, notification, OTP, payment, secret, group-chat, attachment, link, background, locked, scheduled, subrun, hook, and executor fixtures fail closed before material is accepted.
- Capture performs no send, reply, reaction, delete, forward, download, link opening, or settings action, and its UI discloses possible read-state changes from scrolling.
- A normal MCP or SDK caller cannot construct PrivateUiCaptureContext or CaptureAuditRef. A transcript without the matching trusted session or canonical subject target is rejected, as are forged public/shareable/web/article/URI/artifact fields; a refused create leaves no empty subject.
- A successful synthetic capture stores only normalized private transcript, provenance, and content-free audit. An aborted capture stores no screenshot, recording, clipboard, credential, account label, thread label, or transcript fragment in RawStore, logs, telemetry, or diagnostics.
- Audit records include keyed scope digest, host, disclosure versions, start/stop time, closed stop reason, engine/guard-derived counts, and boundary refusals, and contain no message body or caller-supplied totals.
- Successful, rejected-ingest, coordinator-abort, and process-recovery fixtures each leave exactly one content-free stop for every written start.
- The same stable opaque conversation locator produces the same source key across label changes, different locators with identical display labels do not collide, and the subject fallback cannot inflate private-source diversity. Two runtimes and a process restart use the same installation key.
- The host-native capture action returns its typed refusal, abort, engine failure (including subject resolution), or `IngestResult` to the task that invoked it while MCP `tools/list` remains exactly five; changed or still-undistilled input reaches a pending job because enqueue is fixed to `now`.
- Revocation prevents subsequent capture while withdrawal/privacy purge removes already stored transcript facts according to the existing deletion contract.
- A binding with unknown screen-data policy or no window/region isolation reports the lane as unsupported and offers paste/export text as the fallback.
- Tests use synthetic windows and messages only; no live personal account or conversation is required.

## Risks

- Some hosts may not expose a trusted native consent result, non-replayable grant, per-frame revocation signal, stable conversation locator, current-task action result, or window-scoped capture primitive. Missing locator alone uses the conservative subject fallback; missing any authorization, liveness, isolation, or result-return primitive makes the lane unavailable rather than permitting a prompt-only approximation.
- Window isolation can still fail because desktop applications change layout or show overlays. Fail-closed conformance fixtures and a narrow first-release scope reduce but do not eliminate visual ambiguity.
- Host data retention is outside Distilly's fact store. The product must keep the disclosure current and avoid saying “fully local” when screen frames are processed by a host service.
- Content-free audit reduces privacy risk but also limits forensic detail. Keyed scope identity, disclosure versions, derived counts, host, and stop reason are intentionally the maximum retained operational evidence.
- A private transcript can still be sensitive after screenshots are discarded. Private-by-default sensitivity, evidence inspection, withdrawal, and privacy purge remain necessary.
