# Work Skill 분석 Prompt

## 과제

**{name}** 의 원자료(문서, 메시지, 이메일 등)를 받게 된다.
거기서 그의 업무 능력과 방법을 추출해 Work Skill을 만드는 데 쓴다.

**원칙: 업무 관련 내용만 추출하고 잡담은 무시한다. 추론하지 않는다. 근거가 있을 때만 쓰고, 없으면 "원자료 부족"이라고 표기한다.**

---

## 공통 추출 항목 (모든 직위에 적용)

### 1. 담당 범위

원자료에서 다음을 식별한다:
- 그가 담당하는 시스템/모듈/사업 라인/제품
- 그가 관리하는 문서 (인터페이스 문서, wiki, runbook...)
- 그의 직무 경계 (무엇이 그의 몫이고 무엇이 아닌지)
- 그가 자주 언급하는 프로젝트 코드명, 업무 용어

```
출력 형식:
담당 영역: [설명]
핵심 시스템: [목록]
관리 문서: [목록]
경계: [무엇을 맡고 무엇을 맡지 않는지]
```

### 2. 업무 프로세스

과제 설명과 회의록에서 추출한다:
- 과제를 받았을 때의 처리 단계
- 방안/문서를 쓸 때의 구조 습관
- 진행 관리와 deadline 처리 방식
- 예외/긴급 상황 처리 방식

```
출력 형식:
과제 접수: [단계]
방안 작성: [구조 설명]
예외 처리: [프로세스]
```

### 3. 산출물 형식 선호

- 표/목록/플로차트/순수 텍스트 중 무엇을 쓰는지
- 결론을 앞에 두는지, 차근차근 풀어 가는지
- 문서 상세도 (극도로 간결/적당/상세)
- 회신/이메일 스타일

```
출력 형식:
문서 스타일: [설명]
상세도: [극도로 간결/적당/상세]
```

### 4. 경험 지식

그가 명시적으로 표현한 경험적 판단, 겪은 실패, 기술적 견해 (원문을 직접 인용)

```
- "[원문 또는 요약]"
- "[원문 또는 요약]"
```

## 직위별 전문 추출

{name} 의 직위에 따라 해당 항목을 중점적으로 추출한다.

---

### 🖥️ 백엔드 엔지니어 / 서버 엔지니어

**기술 규범**:
- 기술 스택 (언어, 프레임워크, 미들웨어)
- 네이밍 규칙 (인터페이스 경로 스타일, 변수/함수 네이밍)
- 인터페이스 설계 (반환 구조, 에러 코드, 페이지네이션, 멱등성)
- 데이터베이스 조작 선호 (ORM vs 네이티브 SQL, 트랜잭션 경계)
- 예외 처리 스타일

**Code Review 중점**:
- 그가 반복해서 언급하는 CR 지적 (N+1, 트랜잭션, 동시성 안전...)
- 그의 CR 코멘트 스타일 (직설적/완곡, [block]/[suggest] 등급 구분...)

**배포와 운영**:
- 그가 주시하는 모니터링 지표
- 운영 장애 조사 단계
- 변경 배포 프로세스

---

### 🌐 프론트엔드 엔지니어

**기술 규범**:
- 기술 스택 (프레임워크, 상태 관리, 스타일링 방식)
- 컴포넌트 분리 원칙 (언제 나누고 언제 나누지 않는지)
- 성능 관심사 (첫 화면, 지연 로딩, bundle 크기...)
- 인터페이스 호출과 에러 처리 방식

**엔지니어링 실무**:
- 코드 규범 도구 (ESLint 규칙, Prettier 설정 선호)
- 테스트 커버리지 요구 (단위 테스트/통합 테스트에 대한 태도)
- CR 중점 (접근성/반응형/호환성에 대한 관심도)

---

### 🤖 알고리즘 엔지니어 / ML 엔지니어

**연구와 실험**:
- 문제 정의 방식 (ML 문제를 어떻게 분해하는지)
- 실험 설계 습관 (베이스라인 선택, ablation 설계)
- 지표 정의 선호 (오프라인 지표 vs 온라인 지표에 대한 태도)
- 그가 자주 쓰는 모델/방법론

**엔지니어링 적용**:
- 학습 프레임워크 선호
- 모델 배포 프로세스
- 데이터 처리 규범

**문서와 결론**:
- 실험 보고서 작성법 (결론 중심/과정 중심)
- 그가 인용하는 paper 또는 방법론

---

### 📱 프로덕트 매니저 / 기술 프로덕트 매니저

**요구사항 처리**:
- PRD 구조와 상세도
- 사용자 스토리/요구사항 경계 정의 방식
- 개발과 정렬하는 방식 (리뷰 방식, 수정 프로세스)

**의사결정 프레임워크**:
- 우선순위 정렬 방법 (RICE/MoSCoW/자체 방식)
- 데이터 기반 vs 직관의 비중
- 요구사항 충돌 처리 방식

**산출물**:
- 그가 전달하는 문서 종류 (PRD/MRD/프로토타입/경쟁사 분석)
- 프로토타입 도구 선호
- 데이터 로깅 설계 참여도

---

### 🎨 디자이너

**디자인 규범**:
- 사용하는 디자인 시스템/컴포넌트 라이브러리
- 주석 표기 방식과 전달 규범
- pixel-perfect 요구 수준

**업무 프로세스**:
- 요구사항에서 시안까지의 단계
- 검수/승인 방식
- 개발 측 구현 정확도 문제를 처리하는 방식

---

### 📊 데이터 분석가

**분석 방법**:
- 자주 쓰는 분석 프레임워크 (퍼널/코호트/A/B 테스트...)
- SQL 스타일 (간결/주석 상세)
- 데이터 시각화 선호 (차트 유형 선택)

**보고서 스타일**:
- 결론 vs 데이터의 비중
- "데이터로 말한다"를 실제로 얼마나 지키는지
- 데이터 이상치/집계 기준 논쟁을 처리하는 방식

## 출력 요구사항

- 언어: 한국어
- 정보가 없는 항목: `(원자료 부족, 관련 문서 추가 권장)` 이라고 표기한다
- 원문 근거가 있는 결론: 따옴표로 원문을 표시한다
- 출력 결과는 그대로 work.md 생성에 쓰이므로, 구체적이고 실행 가능해야 한다. "아마도", "~하는 경향이 있다" 같은 모호한 표현을 쓰지 않는다
